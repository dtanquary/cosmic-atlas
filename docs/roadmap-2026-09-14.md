# Cosmic Atlas phased improvement plan

Requested 14 September 2026. Status: **planning complete; implementation has not started**. This document sequences all ten ideas discussed with Dave. It is a proposed delivery plan; existing requirements and validation records continue to describe the shipped application.

The recommended order is to establish a baseline, improve the tour experience, optimize its loading and sustained performance, then add photographs, custom trips, slicing, size comparisons and narration. Each phase should deliver a usable increment. Relative effort below expresses scope and uncertainty, not a calendar promise.

| Phase | Result | Relative effort | Depends on |
| --- | --- | --- | --- |
| 1 | Repeatable desktop and phone performance baseline | Small–medium | Current release |
| 2 | Clearer tour stops, comfortable pacing and easier navigation | Medium | 1's browser baseline |
| 3 | Prepared destinations and measured performance improvements | Large | 1 and 2 |
| 4 | Real photographs beside the galaxy models | Medium | 2; reuse 3's resource budgets |
| 5 | Links to individual stops and custom shareable trips | Large | 2 and 3 |
| 6 | An interactive slice through the observed cosmic web | Large | 1 and 3 |
| 7 | Galaxy comparisons at a common physical scale | Medium | 1 and 2 |
| 8 | Optional narration and a final combined release check | Medium–large | 2 and 3; final check follows all phases |

Phases 4–7 can be reordered after their dependencies are complete. Finish and validate one rendering change before starting another so performance and visual regressions remain attributable. Device access or image permissions may leave a specific deliverable pending while independent work continues.

**Phase 1 — Establish the baseline**

Deliver a repeatable route and a concise report before changing runtime performance. Use the current production package and record the exact source commit, browser, device, viewport, drawing resolution and settings.

- Exercise cold and warm startup, the complete road trip, Andromeda orbit, Coma, the survey overview, and 10–15 minutes of mixed exploration. Include an ordinary network and a reproducibly throttled connection.
- Record first navigable view, camera arrival versus useful visual arrival at each stop, frame-time distributions during movement, stutters, transferred bytes, outstanding requests and managed allocations. Separate loading from steady-state rendering and compare early and late portions of the longer session.
- Run desktop Chrome on the actual GPU and WebKit phone layouts. Add a physical iPhone run when available; record device/OS and observed warmth or battery change separately from renderer measurements. Do not infer temperature or power from frame rate.
- Keep any temporary diagnostic UI unobtrusive and opt-in. Reuse existing statistics and GPU probes; a new telemetry service is unnecessary.
- Reconcile stale desktop-only/mobile-deferred wording in requirements with the already shipped mobile controls when documenting this baseline.

Acceptance: the browser route is reproducible, resource and loading costs are separated, and a ranked list of measured bottlenecks identifies the work for phase 3. Preserve the existing desktop targets; define phone acceptance targets from recorded device evidence before tuning. If a physical device is unavailable, mark that part pending and proceed with browser work without claiming physical-device validation.

First milestone commit: benchmark journey and baseline report. This phase need not change the public application.

**Phase 2 — Improve the road trip and orientation**

Deliver a tour that tells visitors where to look, gives them time to explore, and makes returning easy.

1. Give built-in stops stable IDs independent of their array positions. Extend the existing tour data with a short visual cue and expandable explanation. Retain source-pinned distance and lookback values; all visible numerical claims remain covered by the source tests.
2. Review every stop at desktop, phone portrait and phone landscape dimensions. Tune camera composition without moving or resizing catalog objects. Keep the current outward Coma framing and distinguish camera pullback from cluster size. Optional highlights should be brief, bounded annotations that do not alter galaxy light, enter picking, or imply a measured cluster boundary.
3. Add Quick / Relaxed / Manual pacing and a compact chapter picker. Quick and Relaxed primarily vary dwell time; Manual uses Prev/Next and never advances automatically. Keep current travel comfort and reduced-motion behavior. Pacing is session state initially, and tours continue to leave saved display settings untouched.
4. Make Explore here and Return to stop / Continue explicit. Navigation input still pauses immediately. Return restores the saved arrival pose; Continue returns first if necessary and then resumes the chosen pace. Closing details never silently resumes travel.
5. Add a bounded session history for Back to previous view. Capture completed navigation destinations and the view before a new deliberate navigation, not every animation frame or tour hop. Back pauses a tour, revalidates selection identities, and does not restore unrelated display preferences. Keep it distinct from the tour's Prev stop action.
6. Add a compact place label using verified selections or curated route context, such as Andromeda / Local Group. For arbitrary positions use distance/context already available; do not infer group membership by proximity. Place secondary actions in existing menus so the desktop layout stays familiar and phone map area remains usable.

Acceptance: all ten road-trip stops and all five zoom-out stops remain reachable; cues are clear and controls unobstructed in portrait and landscape. Test chapter jumps, interruption during lookup/travel/dwell, Manual behavior, return after orbit, Back after a shared view, reduced motion, tab hiding and graphics recovery. No stale operation may reclaim the camera. Existing invitations still start the standard road trip once and ordinary view links remain compatible.

Milestone commits: stop IDs/content and framing; pacing/chapter/return behavior; history/place UI; actual-GPU and production evidence. Extend `tour.ts`, the existing app/mobile controls and view-state helpers rather than introducing another camera controller.

**Phase 3 — Prepare destinations and improve sustained performance**

Deliver visibly prepared stops and optimizations justified by phase 1. Implement and measure the loading work separately from rendering changes.

1. Add cancellable preparation for the next stop only. Use the existing loader, exact identities, cache accounting and a conservative request/byte allowance established from the baseline. Current-view loads and explicit navigation take precedence. Preparation must not select, focus, allocate a visible replacement model, evict an on-screen model, or expand the 12-model DESI pool.
2. Give speculative requests their own cancellable ownership. The current loader preserves priority and metadata requests across frontier changes, so simply marking speculative work as priority would be insufficient. Pause, chapter changes, Exit, tab hiding and newer navigation release obsolete preparation without cancelling a shared load needed by the visible view.
3. Introduce a destination-readiness signal tied to the current stop and cancellation generation. For a galaxy, require its usable point/model representation in the arrival view; for a cluster or overview, require useful coarse coverage of the destination region. Do not wait for all requests or the entire catalog. Start dwell after camera arrival and readiness, with a finite timeout and a readable partial-data/retry state. Unavailable identities still follow the existing skip behavior. Keep a single active tour scheduling timer, reusing it across readiness and dwell states.
4. If measurements identify pixel cost, add gently adaptive scene resolution with bounds, hysteresis and a recovery delay. Keep DOM text sharp and preserve CSS-space point sizes, pointer coordinates and picking. Keep reduced resolution visible only as a rendering-quality choice; full detail must retain its complete observation frontier.
5. Profile the 0.5% background floor independently. It currently bypasses distance-only chunk culling, so investigate a cheaper coarse distant frontier in Adaptive mode if its cost is material. Preserve the floor, exact sampled identities, positive-floor picking, coverage accounting and local-position guard. Never silently sample Full detail. Do not change the floor or claim equivalent photometry as a shortcut.

Acceptance: compare the same cold/warm routes and sustained sessions against phase 1, recording bytes and allocations as well as frame time. Preparation stays bounded during rapid Prev/Next and cancellation; a slow or failed load never traps the tour. Resolution changes do not oscillate, move hit targets or destabilize models. Keep a candidate only when its relevant metric improves beyond observed run-to-run variation without a material visual/navigation regression. An optimization experiment that brings no benefit is documented and reverted; the investigation is still completed.

Milestone commits: preparation lifecycle; readiness/timing; each independently supported rendering optimization; before/after results. Physical-phone performance remains unverified until the device run is completed.

**Phase 4 — Compare models with real photographs**

Deliver an optional See photograph action for supported road-trip galaxies, with attribution and an honest comparison to our illustrative model.

- Start with Andromeda and one Magellanic Cloud to exercise disk and cloud layouts, then cover the remaining supported road-trip galaxy targets. Desktop can show the image beside the model; phone uses a bounded photograph/model switch that preserves the camera and tour state. Opening comparison pauses the tour; resumption is explicit.
- Build a compact exact-identity manifest with source page, image asset, credit/license, field of view and any verified orientation information. Reuse the research in `image-portraits.md`. Reference links are currently not redistributed assets: verify each image's reuse terms before packaging it, keeping source originals out of Git and tracking preparation scripts, manifests and attribution.
- Add Match observed view only where image orientation and field framing are supported. Unknown crop rotation or missing orientation disables matching with a short explanation. The image is an observation from our direction; it does not become a texture projected onto an invented 3D surface.
- There is no external photograph of the Milky Way. Its card may show an explicitly labeled inside-the-Galaxy panorama. A Coma field photograph can illustrate the cluster without assigning missing galaxy identities; a survey graphic must be labeled as a map, not a telescope photograph.
- Use small prepared assets, lazy loading and a bounded decoded-image cache. Verify package size and licensing for every new asset. Legacy Surveys documents JPEG cutouts and viewer links, providing a possible source for later coverage; availability and permission are verified per asset. [Image service documentation](https://www.legacysurvey.org/viewer/urls/)

Acceptance: every supported photo maps to the exact intended object; credits are reachable; unsupported views have a useful fallback. Compare scale/orientation visually where claimed, check image failures and slow loading, and verify desktop/phone interaction, camera restoration and resource disposal. The live atlas must remain usable without the images.

Milestone commits: image manifest/preparation and first comparison; remaining supported targets; verified production layouts and budgets.

**Phase 5 — Share stops and build custom trips**

Deliver the smaller stop-link feature first, then a local itinerary editor using the same tour runner.

- Copy link to this stop uses a stable route/stop ID and opens that destination paused, with Continue available. Keep the existing whole-road-trip invitation's autoplay semantics. Version new link forms and keep the original strict view-link and invitation formats working.
- Let visitors add verified destinations or existing saved camera views, reorder them with buttons as well as drag, remove stops, and add a title and short plain-text caption. A camera-only view stays camera-only; a user's caption is distinguished from sourced atlas facts.
- Save custom trips locally without accounts. Use a bounded, validated, versioned fragment payload for sharing. Initial proposed limits: 10 stops, a 60-character trip title, 180-character captions, and an 8 KiB encoded link ceiling; test Unicode and actual messaging/browser round trips before fixing the limits. Show a clear size limit rather than silently truncating content. File export/import can carry trips that exceed the tested link size.
- Revalidate identities on every open; never trust dense IDs or serialized executable content. An unavailable catalog destination can fall back to its explicit saved camera with a notice, consistent with ordinary shared views; a stop with neither valid identity nor camera is skipped with an explanation. Unknown schemas and malformed/oversized payloads must leave the atlas navigable.
- Opening a custom trip shows its itinerary with a Start action. Neither custom captions nor imported data can persist display settings or bypass the local-position guard. Only the established built-in invitation keeps automatic start. These are intentional new payload types; ordinary view links continue to contain only camera, target and identity.

Acceptance: share a built-in stop and a custom route between fresh browsers, revisit it in an open tab, edit/save/delete locally, and handle blocked storage/clipboard, Unicode, corrupted IDs, excessive lengths and subset omissions. Input cancels pending starts. Reload/context recovery never reapplies a consumed invitation. All playback uses the existing cancellation and readiness behavior.

Milestone commits: versioned stop links; local editor/playback; custom serialization and recipient experience; production round trips.

**Phase 6 — Slice through the observed cosmic web**

Deliver an optional movable slab through the DESI point catalog, with position, thickness and orientation controls and a clear Exit slice action.

- Begin with one useful preset and a thickness slider, then add position and orientation after validating clarity and cost. Use the existing point shaders and CPU node bounds to cull whole excluded chunks; never build a second full catalog or one object per record.
- Apply the same slice rule to visual points, GPU ID picking, DESI models and selection/measurement annotations. Preserve inspected values while clearly indicating an out-of-slice target. Keep total accepted counts unchanged and label visible/submitted counts as filtered. Define Full detail as all eligible observations inside the active slice, subject to the existing local guard and memory reporting.
- Make the initial scope explicit: the slice filters DESI observations. Nearby and Milky Way references remain separately identified context layers and do not enter slice counts. Keep survey-footprint context available and explain its angular-only meaning; occupancy cannot establish radial completeness or confirm that a gap is a void.
- Clear the slice on a deliberate tour start and restore the prior slice state on tour exit without saving changes. Explicit focus on an out-of-slice object offers an intentional way to reveal it instead of navigating to an invisible target. Ordinary view links do not silently acquire slice settings.
- Show the galaxy distribution itself. Do not add fabricated gas, dark-matter surfaces, inferred filament connections or named-void claims. DESI's own slice examples illustrate why this is useful. [DESI map slices](https://www.desi.lbl.gov/2021/07/22/the-beginnings-of-the-3-dimensional-map/)

Acceptance: analytically known boundary points agree between visual and ID passes; node culling never removes intersecting eligible points; slicing/refining preserves parent/child coverage and identity. Exercise adaptive/full detail, positive opacity floors, local guard, models, measurements, tours, subset data and context recovery. Benchmark interactive sweeping and inspect real survey captures to assess whether structure is actually easier to read.

Milestone commits: coherent visual/picking filter; controls/counts/context; streaming/model/annotation integration; scientific and GPU validation.

**Phase 7 — Compare galaxy sizes**

Deliver a separate comparison view for the Milky Way, Andromeda, Triangulum and both Magellanic Clouds at a common physical scale.

- Use the existing model definitions and a small bounded comparison layout. Reposition representations only within this explicitly separate diagram; leave atlas coordinates, measurements and identities untouched. Reuse available fields/geometries and dispose transient resources when closing.
- Draw one shared physical ruler and explain each adopted radius/extent convention. Audit the size sources first: half-light radii, optical diameters and illustrative model envelopes are different quantities. Do not present them as interchangeable measured edges. Retain assumed cloud dimensions and uncertainty labels.
- Allow a small selected group, with a phone-friendly layout and larger labels rather than shrinking everything into illegibility. Avoid normalizing every object to the same apparent size. Returning restores the atlas view and a paused tour.
- Verify that comparison allocations stay bounded without silently doubling the nearby field budget or enlarging the DESI pool. If simultaneous rendering cannot meet the budget, share immutable resources or render cached comparison views sequentially.

Acceptance: displayed physical ratios match the documented adopted definitions; no hidden per-galaxy rescaling is introduced. Review the five objects at common scale on desktop and phone, preserve source profiles and deterministic appearance, and test repeated open/close/context recovery for leaks and exact return behavior.

Milestone commits: size-definition audit and first comparison; all five objects and responsive controls; geometry/GPU/production evidence.

**Phase 8 — Narration and combined validation**

Deliver optional spoken narration for a short Our galactic neighborhood route built from existing stops, then extend it to the full road trip once pacing works.

- Draft short scripts from the source-checked captions and establish one narrator voice. Prepare licensed/authorized audio assets with transcripts; keep the text tour fully functional when audio is absent. Custom trips remain text-only in this phase.
- Require an explicit Listen action. Existing shared tour links stay silent until audio is requested; browsers can block programmatic audible playback, so handle rejection and retain reachable controls. [Browser autoplay behavior](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- Tie audio to stable stop IDs and the existing tour generation. Arrival readiness gates speech; Pause, Explore, Prev/Next, Exit, tab hiding and context loss pause/stop obsolete audio. Use audio completion events to inform the existing single dwell scheduler, not a second tour timeline. Manual pacing never advances on audio completion; missing or failed audio falls back to text pacing with a notice.
- Load only the current and, within budget, next clip. Provide mute, replay and transcripts; reduced-motion users retain instant travel. Audio completion from an old stop must not advance a newer one.
- Repeat the combined desktop/phone journeys with all new features installed, including custom-trip → photograph → return → slice → comparison → narrated-tour transitions. Verify saved settings, ordinary links, consumed invitations, counts and old controls still work.

Acceptance: narration follows the correct stop without overlap, drift or unwanted autoplay, and is usable on actual Safari/Chrome browser engines. Perform physical-phone audio/background-interruption checks when a device is available, marking any untested hardware behavior explicitly. Scripts, transcripts, source claims and asset credits agree. The complete package and final live deployment pass the shared release gates below.

Milestone commits: scripts/transcripts and first narrated route; road-trip coverage and interruption handling; final integrated evidence.

**Validation and delivery gates**

Every implementation milestone gets a staged diff review, appropriate checks and a small coherent commit. Add meaningful lifecycle/data/rendering regressions where behavior changes; typography-only adjustments need visual verification rather than implementation-mirroring tests. Update requirements, architecture, galaxy-detail documentation where relevant, tours/image documentation, UI review and validation notes as behavior ships. Keep planned performance targets separate from measured results.

| Change | Required focused evidence, in addition to applicable unit checks |
| --- | --- |
| Tour, camera, history, pacing, readiness, links or narration controls | Actual-GPU `?tourtest&uxtest&hometest&sharetest`; subset tour skip behavior; ordinary and invitation production journeys |
| Phone controls or new responsive panels | `scripts/check-mobile-ui.mjs` on Chrome and WebKit, real Chrome touch gestures, portrait/landscape and repeated desktop restoration; extend journeys for new controls |
| Point sizing, opacity, resolution or background frontier | `?selftest`, full-data `?hometest`, `?uxtest`, `?continuitytest`; visual/ID agreement and measured before/after routes |
| Model appearance, geometry, rendering reuse or residency | Applicable `?portraittest&cloudtest&hometest&nearbytest&continuitytest&varianttest&colortest`; nearby full/subset, actual road trip, bounded allocations; `npm run test:models` |
| New slice | New boundary/coverage/filter GPU regressions plus shared UI/home/tour/model suites; full/subset and both detail modes |
| Shell, lookback or footprint changes | `?lookbacktest&cosmictest`; `?footprinttest` on full/subset if footprint behavior changes |

Before publishing each releasable phase: run the applicable checks, the full test suite and strict build, inspect its production package on the actual GPU, run `npm run build:pages` and `npm run release:audit`, push the coherent commits to GitHub and deploy through the existing Cloudflare workflow. Verify hosted hashes/counts/assets and the changed user journeys. Preserve all 14,140,375 accepted observations, six separately counted nearby entries, model/resource bounds, source identities, saved choices and the 0.5% default. Package size must remain within verified host limits after adding media.

Publish the designated public app and tour launch links in the README. Other hosting details, account identifiers and operational receipts stay in ignored `.deploy/`; public validation documentation records source commits and sanitized evidence. Retain the previous verified deployment for rollback. A pending physical-device check is reported as pending rather than represented as a passed simulated check.

**Decisions to resolve during the relevant phase**

The plan uses small defaults so work can proceed without a design interview: existing visual style; familiar desktop layout; session-only pacing/history initially; silent invitations; no account/backend for custom trips; optional photos, slicing, comparisons and audio. Phase 1 determines which performance experiments are justified. Phase 4 establishes image rights and supported orientation matches. Phase 5 measures usable link limits. Phase 7 establishes comparable size conventions. Phase 8 selects the final voice after scripts exist. These decisions do not block earlier independent phases.
